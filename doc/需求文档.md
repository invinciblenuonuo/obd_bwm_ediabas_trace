# OBD Logger 需求文档

> 关联文档：[项目背景.md](./doc/项目背景.md)（环境、目录、配置、已验证/未验证项的事实来源）

## 1. 总目标

开发一个 Windows 桌面端程序（最终形态为车辆数据记录器，logger），通过 EDIABAS 原生 API（`api32.dll`）与 EDIABAS 建立连接；EDIABAS 加载 PRG 文件（SGBD），经由 K+DCAN 线连接宝马 E84（N20 发动机）的 OBD 接口，与车辆 ECU 通信并获取数据。

整体链路：

```text
本程序 → api32.dll → EDIABAS(7.3.0) → mevd1724.prg → K+DCAN(COM6) → E84 N20 DME
```

## 2. 技术约束（来自背景调查，属硬性前提）

| 编号 | 约束 | 说明 |
| ---- | ---- | ---- |
| TC-1 | 必须 32 位进程 | `api32.dll` 为 32 位，64 位进程无法直接加载；本机 Python 3.11 / Node.js 22 均为 64 位 |
| TC-2 | 推荐技术栈 C# / .NET | 项目需设置 `PlatformTarget=x86`；`C:\EDIABAS\Bin\TestCsNET32.exe`、`apiNET32.dll`、`Api32\EdiabasLib.config` 表明 C# 路线有官方/社区现成参考 |
| TC-3 | 运行环境固定 | 依赖 `C:\EDIABAS\` 目录结构、`EDIABAS.INI`（`Interface = STD:OBD`）、`obd.ini`（`Port=Com6`）；PATH 已含 `C:\EDIABAS\Bin\` |
| TC-4 | 硬件通道固定 | FTDI K+DCAN 线，COM6（已验证可打开/关闭）；与 INPA/Tool32 共用同一线，存在端口占用冲突 |
| TC-5 | PRG 文件 | `C:\EDIABAS\ECU\mevd1724.prg`（DME 诊断 Job 定义，仅诊断，不是刷写程序） |
| TC-6 | 安全红线 | 一期只允许调用识别/状态类只读 Job；禁止任何写入、复位、编程类 Job |

## 3. 一期需求：链路打通 + 命令行打印车辆基础信息

### 3.1 一期目标

验证"程序 → EDIABAS → K+DCAN → 车辆 DME"整条链路可用，并从 DME 读取真实的车辆基础信息打印到命令行。**一期只做只读诊断，不做数据记录、不做写入。**

### 3.2 功能需求

| 编号 | 需求 | 优先级 |
| ---- | ---- | ------ |
| FR-1 | 以 32 位（x86）进程运行，成功加载 EDIABAS API | 必须 |
| FR-2 | 调用 `apiInit()` 完成 EDIABAS 初始化，使用现有 `EDIABAS.INI` / `obd.ini` 配置（STD:OBD / COM6） | 必须 |
| FR-3 | 加载 SGBD `mevd1724`，与 DME 建立诊断通信 | 必须 |
| FR-4 | 调用识别类 Job（如 ECU identification），并通过 `apiResult...()` 系列函数读取返回值 | 必须 |
| FR-5 | 将结果格式化打印到命令行（字段名 + 值 + 单位，如有） | 必须 |
| FR-6 | 正常结束时调用 `apiEnd()` 释放资源；异常路径同样保证释放 | 必须 |
| FR-7 | 完善的错误处理：API 错误码、ECU 无响应、COM6 被占用、未接线/点火 OFF 等场景给出明确人类可读提示，进程不崩溃、不挂死 | 必须 |
| FR-8 | 应用层日志：记录每次 API 调用、Job 名称、关键参数与结果，便于排障（可写文件或控制台） | 建议 |
| FR-9 | 失败时可提示开启 EDIABAS 侧 `ApiTrace`/`IfhTrace` 辅助定位（文档说明即可，程序不强制改配置） | 可选 |

### 3.3 "车辆基础信息"定义（一期输出清单）

必须输出（MVP）：

- VIN 车架号（用于人工比对车辆铭牌，验证读到的是真实车辆数据）
- DME/ECU 识别信息：ECU 名称或诊断标识（用于确认实际 DME 是否为 MEVD1724）
- ECU 硬件号 / 硬件版本
- ECU 软件号 / 软件版本

可选输出（有余力则做，一期不强制）：

- 点火开关状态（KL.15）
- 蓄电池电压

> 具体 Job 名称与结果字段以 `mevd1724.prg` 中实际定义的识别类 Job 为准，开发阶段需先列出该 PRG 可用的只读 Job 清单。

### 3.4 非功能需求

| 编号 | 需求 |
| ---- | ---- |
| NFR-1 | 单次执行从启动到输出结果 ≤ 30 秒（不含人工点火操作） |
| NFR-2 | 程序为命令行应用，零安装依赖（除已有 `C:\EDIABAS\` 环境），双击/命令行即可运行 |
| NFR-3 | 代码结构上将"EDIABAS API 封装层"与"业务输出"分离，为二期数据记录功能预留复用 |

### 3.5 验收标准

| 编号 | 场景 | 通过条件 |
| ---- | ---- | -------- |
| AC-1 | K+DCAN 接车、点火 ON | 程序初始化成功，与 DME 建立通信，退出码 0 |
| AC-2 | 同上 | 命令行打印 3.3 节全部"必须输出"字段；VIN 与车辆铭牌一致 |
| AC-3 | 同上 | 根据 ECU 识别信息确认 DME 型号（回答背景遗留问题：E84 N20 是否为 MEVD1724） |
| AC-4 | 未接车 / 点火 OFF | 明确提示连接失败原因，进程正常退出，无异常堆栈 |
| AC-5 | COM6 被 INPA 等占用 | 明确提示端口不可用及可能原因，进程正常退出 |
| AC-6 | 全程 | 仅调用只读 Job，无任何写入/复位/编程类调用（代码评审确认） |

### 3.6 一期明确不做（Out of Scope）

- 实时数据流/定时采样与落盘（二期）
- 故障码（DTC）读取与清除（二期及以后；清除属写操作，需单独评估）
- GUI 界面
- 任何写入、复位、编程、刷写操作

## 4. 技术方案建议

推荐：**C# 控制台程序，`PlatformTarget=x86`，.NET Framework 4.8**（与背景环境一致，兼容性最稳）。

API 封装两选一：

1. 直接 P/Invoke 调用 `api32.dll`（`apiInit`/`apiJob`/`apiResult...`/`apiEnd` 等）—— 依赖最少，完全可控；
2. 使用机器上已有的 EdiabasLib（`C:\EDIABAS\Bin\Api32\` 下有其 config，社区成熟的 .NET 封装）—— 开发快，但需确认版本与许可。

## 5. 风险与待验证项（继承自背景文档）

| 编号 | 风险/未知 | 应对措施 |
| ---- | --------- | -------- |
| R-1 | E84 N20 实际 DME 可能不是 MEVD1724 | 一期首个实车动作即读取 ECU 识别（AC-3），若不符则更换匹配 PRG 后重试 |
| R-2 | ECU 握手未验证（目前只测过 COM6 开关） | 按 AC-1/AC-4 验收；失败时开 ApiTrace/IfhTrace 排查 |
| R-3 | 车辆电压不足导致诊断中断 | 诊断前确认电压正常（可纳入可选输出），必要时接充电器 |
| R-4 | K+DCAN 线质量/时序兼容性（廉价 FTDI 线常见问题） | 若握手失败，先用 INPA/Tool32 验证线缆与车辆通信正常，再回到自研程序排查 |
| R-5 | 端口占用冲突 | AC-5 验收；使用说明中注明"勿与 INPA/Tool32 同时运行" |

## 6. 后续阶段展望（呼应 logger 定位，仅记录方向，非本期承诺）

- 二期：实时运行数据（转速、水温、油温、车速、节气门等）的定时采样与 CSV/文件落盘
- 三期：故障码读取、历史记录管理、简单图表展示
- 长期：Job 配置化（外部配置文件定义采样项）、数据导出分析
